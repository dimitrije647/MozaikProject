# Incident fixtures (2026-11-02): Hybrid Production run, F4 could not read the F3 strategy

Three saved rows from the real failed run, **sanitized** so they carry structure but no business content:

| file | table | what it is |
| --- | --- | --- |
| `f1-row.json` | `ProductDiscoveryReport` | the reused F1 report (schema version 2) |
| `f2-row.json` | `MarketingAuditReport` | the reused F2 audit (schema version 1) |
| `f3-row.json` | `MarketingStrategyReport` | the F3 strategy that F4 refused to read (schema version 1) |

What the incident was: F3 stored `creativeBrief.claimsToAvoid` with **9** entries (6 written by the strategist, 3 added from the Marketing Audit's
flagged claims; the producer allowed up to 12) while the schema that F4 reads allowed **8**. F4 failed 76 ms after F3 finished.

## How they were made

Generated by a deterministic script from read-only copies of the three rows (the database was never written):

* every key, the nesting, numbers, booleans and nulls are kept;
* enum-like and id-like strings are kept (channel, role, status, finding ids, ...);
* every list keeps its length (lists longer than 20 are cut to 20, except the lists of findings, which are kept whole: they decide which claims the audit flagged);
* every other string is replaced by a neutral placeholder **of the same length** (so every `max`/`min` rule behaves as it did);
* real ids are replaced by `fx-*` ids, consistently across the three rows (the lineage between them is intact);
* no e-mail address, key, URL or business text is present (URLs are `https://fixture.invalid/...`).

Checked when they were made: the pre-fix contract rejects `f3-row.json` with exactly one issue (`creativeBrief.claimsToAvoid`, too many, limit 8);
the current contract reads all three as `current`.
